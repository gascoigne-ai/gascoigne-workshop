# internal

Loaded when you work under `internal/`. Adds to `.harness/rules.md`.

- `internal/<domain>/<package>`; domains `request`, `collection`, `response`, `settings`, `workspace`; the root package `internal/<domain>` (named after the domain, so `request`, `collection`, `response`, `settings`, `workspace`) holds the domain types, their rules and the ports at its boundary; zone directories are only `ui` (views and input) and `adapter` (implementations of ports: network, files, system); a controller (state and decisions, no widget and no I/O) is a package sitting directly under its domain, not a directory.
- Dependencies point inward: the domain root imports no other package of its domain (the leaf packages it needs, such as `fileversion` or `clientconfig`, import it never); a controller imports the root and controllers, and neither the toolkit, Ebitengine nor `net/http`; ui imports the root and controllers, never an adapter or another ui package; adapter imports the root, controllers and the adapters of its own domain, never a ui; another domain is reached only through its root package (`workspace` may also import their ui and controller). A new package goes into a domain (or its `ui` or `adapter` zone); no `utils`, `common` or `helpers`.
- Import a domain root without an alias, as `request.Request`. Locals that would shadow the package are renamed (a request value is `call`), never the import: the naming rule forbids short parameter names.
- `internal/app` (the `App`) is the composition root and may import any package. UI-free state and decisions go to a `controller` package; a controller never imports the toolkit.
- Exception, written: `internal/settings/theme` sits directly under its domain and imports `uitoolkit/core` and `uitoolkit/theming`, because theme data is toolkit-bound; its package doc says why.
