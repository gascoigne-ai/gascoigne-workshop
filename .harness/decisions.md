# Decisions

Current facts only. Each entry keeps its date and the reason; history that no longer matches the code was dropped in task 060.

1. **Ebitengine with custom widgets** (user choice). Pure-Go GPU 2D with Wayland, X11 and one static-ish binary. Cost: every widget, text input and scroll area is ours.
2. **Protocols are a table; streaming and MCP are hand-written, gRPC is official.** `model.Protocol` is a named type whose values are the rows of `model.Protocols` (`rest`, `websocket`, `mcp`, `sse`, `grpc`; label, connection, method kind, whether it runs a command, the header that resumes a stream), and `request/port.Registry` maps each row to its implementation. Per-protocol behavior is a row of `model.Protocols` and of the app's `protocolViews` (panes, composer, the chip's settings switch); nothing compares a protocol, and `internal/protocol_literals_test.go` enforces it (task 078, 2026-11-18). The table is split because the UI half names panes and the model half is needed by packages that may not import the UI or `proto` (editor, access, Postman export). An unknown or empty protocol text is a parse error at the edge (user's decision, 2026-11-18): a collection request file with one fails the load with an error naming the file, as a malformed file does; a `.workshop` client config reports the server or request; a sent-log line is skipped. Body and auth types are named types too: `BodyRaw` ("") is the legacy raw body, `AuthNone` ("") is no authentication and the older stored `"none"` still reads as it. `Send` is one-shot; a protocol that stays connected also implements `Streamer.Connect`, which returns a `Session` (ordered `Events()`, `Send`, `Ping`, `Close`; a slow consumer blocks the reader, nothing is lost). WebSocket (RFC 6455, `request/adapter/proto/ws`, about 400 lines) and MCP (JSON-RPC over streamable HTTP and `stdio:` commands, `proto/mcp.go`) are written by hand: the needed part is small, the rules allow no new dependency, and the raw message log the UI shows is what the client already handles. gRPC uses `google.golang.org/grpc` and `protobuf` (approved by the user 2026-11-06), since HTTP/2 and protobuf are not a small part: reflection through grpc's own clients, messages are `dynamicpb` with `protojson`, the methods from reflection or from `.proto` files read at run time (decision 19), no generation. gRPC URL is `grpc://host:port` or `grpcs://` (TLS, `InsecureTLS` honored), `Method` is `package.Service/Method`, `Body` is the message JSON. A call that reached the server is a response whose `Status` is the HTTP equivalent of the code (`OK` 200, `NOT_FOUND` 404, `UNAVAILABLE` 503, others 500) and `StatusText` the code name, so the status pill and `status == 200` assertions work; a call that could not be made is `Response.Err`. A request is a unary call; the Stream chip of the strip turns a gRPC tab into a stream shown in the Messages pane.
3. **The toolkit is three layers, independent of the app** (2026-11-11, user's correction of an earlier attempt). `core` holds primitives only (tokens, colors and color math, geometry, input, clipboard, fonts, the `Ctx` drawing calls); `view` is the framework (element tree, layout, runtime, generic options, the extension point `Behavior`/`Custom`/`Base`, `Linear`, `Describer`, `Focusable`, `Focuser`, `PreUpdater`, `OverDrawer`, `Scroller`); `widget` is every component with its own drawing, input or state (buttons, menus, dialogs, tabs, icons, scroll areas, split, slider, table, tooltips, `Field`, `Area`, `Code`); `markup` builds both from templates; `theming` imports only `core`; `engine` holds key bindings and frame pacing. Like Qt, GTK and Flutter, the base holds no component. `view` cannot import `widget`, so a component leaves `view` only when nothing there uses it and what the runtime calls goes through an interface. A component is a `view.Custom` behavior that reads its look through `FixedSize`, `ColorToken`, `HoverColorToken`, `El.ControlName`. `uitoolkit/core/layers_test.go` enforces the imports; runnable examples are one package, `uitoolkit/examples`, because `go vet` forces the `Example_xxx` form. The package `vml` was renamed `view` (user's choice, task 029); `VML` is the template language and `.vml` its file extension.
4. **Views are markup templates** (2026-11-12, user's choice; reopens the earlier "tab strips, tables and App features stay Go"). A template is XML with HTML's leniency, parsed with `encoding/xml`, and builds the same `*view.El` tree as the Go builders (`Row`, `Col`, `Text`...). Elements and attributes are tables (`elements`, `attributes`, one row per element with its `params`), bindings are `{{path}}` lookups in a `Scope`, directives are `if` and `for="x in xs"`; no expressions, so logic stays in Go and templates stay checkable. Errors name file and line. Scope values are typed Go values: a path reads a map key or an exported struct field through pointers, `for` walks any slice, `if` reads a value by its kind, methods are not reachable (one name, two meanings). Container elements take state and specs from the scope by name as Go types (`state="scroll"`, `items="tabs"`, `spec="spec"`); a nil state pointer is a build error naming the entry. An option is switched off by its value (an empty color token, `separator="0"`), so one template serves an item with and without it. Handlers are attributes (`on-click`, right and middle click, drag over, select, dismiss, change, enter, slide, tab). `ResizableDialog` bounds are `min-width`, `min-height`, `max-width`, `max-height`. A view moved to markup may not change a pixel; golden shots (decision 5) and `view.Dump` pins are the oracle. Templates are inline strings in the Go file of their view (task 061, user, 2026-11-15), in a `const` at its end and parsed once with `markup.Must("name.vml", nameSource)`; there are no `.vml` files in the app, and `markup.Load`/`MustLoad` over an `fs.FS` stay in the toolkit as API. Template names keep the `.vml` form so errors and docs read as before. `widget.ActiveTab()` is the open tab's look, shared by `Tabs` and the request strip. Views are rebuilt every frame: state stays in the app, widgets that need identity across frames take a pointer to app-owned state, there is no diffing and no reactive graph.
5. **UI changes are checked against golden shots drawn with software GL** (2026-11-12, user's choice over a Go rasterizer or Xwayland). Ebitengine draws only through a GL context, so `cmd/workshop/softshot_test.go` runs the program on Mesa llvmpipe under Xvfb; `TestGoldenScenes` compares each scene with `cmd/workshop/testdata/golden` (4 per channel, 100 pixels of slack, durations masked), and is skipped without `xvfb-run` except in CI.
6. **Themes are data, per control.** Colors, radii, gradients and outlines are embedded JSON theme files (variables, colors, controls), so the look can change (settings `corners`, `flat`) without touching widgets. Elements name a control style (`view.Control`) rather than picking a gradient. Own small JSON, because it has to carry radii and gradients and parsing stays in the standard library.
7. **Collections are a tree of JSON files** (`collection/adapter/store`). One directory per folder (`folder.json`: name, root variables, child order), one `*.req.json` per request, stable key order, so diffs are small. File names are slugs made unique with `-2`, `-3`; the real names live inside. Credentials go to `.secrets.json` keyed by request path and listed in `.gitignore`, never into request files. Saving removes only `*.req.json` files and folders with a `folder.json`; other files are left alone. Files the order list does not know load after the listed ones, by name. Whole collections are managed from the UI (task 063, user's choices 2026-11-15): several can be open (task 071); New makes a folder in `collections/` beside the default workspace and opens it beside the open ones, Rename moves the folder to the new name's slug, Delete removes only the files the store wrote (a user's README or a `.gitignore` with other lines stays, and so does the folder) and opens the next collection or a new empty one; the actions are on a right-click menu of the Collections chip and of the collection's root row, which also closes it and moves it up or down among the roots.
8. **Native file dialogs shell out to osascript (macOS), PowerShell (Windows), zenity, kdialog, yad, qarma or matedialog** (`workspace/adapter/filedialog`), no widget and no dependency. On Linux the programs are tried in the order the desktop prefers (task 068, user, 2026-11-15): a table of desktops read from `XDG_CURRENT_DESKTOP`, `XDG_SESSION_DESKTOP` and `DESKTOP_SESSION`, no D-Bus. The dialog runs off the UI goroutine and answers through the bus; without one of these programs the app opens its in-app file browser (decision 18).
9. **settings.json is one schema table** (task 030). `settings.Schema` lists every key once (title, description, kind, allowed values, range); the form, raw text view, validation, completion, per-setting reset and `Minimal` all read it. The file holds only what differs from the defaults; reset removes the key. The raw view reuses `TextArea`: errors color the offending key through `Styler` plus a list with line and column, completion is a menu opened by Ctrl+Space at the caret. A valid raw edit applies at once; an invalid one changes nothing. The file is checked for outside changes every 30 frames. Edits have two entry points: `saveSettings` (applies, rebuilds protocols on a network change, refreshes tabs on a response-view change, persists) and `changeSettings` (the same plus `colors.Forget`, for the dialog's own controls only: the Colors page edits through `saveSettings` while a hex field is typed).
10. **Client configs are `.workshop.{yaml,json,toml}`; debug builds carry example endpoints** (user approved 2026-11-10). A client is a collection with requests and environments, or a named server connection. A release build (`-tags release`) has no sample and reads a global file in the settings directory and a local file in the working directory; a local entry replaces a global one of the same name; two files of different formats in one directory are an error. JSON uses `encoding/json`, YAML the `miniyaml` subset reader, TOML `github.com/BurntSushi/toml` (approved by the user). The default build's sample points at `cmd/example-server`, one port per protocol and a second gRPC port without reflection (task 070).
11. **`internal/` is `<domain>/<role>/<package>`** (task 033, user's choice 2026-11-07). Domains `request`, `collection`, `response`, `settings`, `workspace`, `environment`; roles `ui`, `controller`, `port`, `adapter`, `model`. `internal/layers_test.go` enforces: model imports only model; port imports model and port; controller imports model, port and controller (and no `uitoolkit`, Ebitengine or `net/http`); ui imports model, port and controller, never an adapter or another ui package; adapter imports model, port, controller and the adapters of its own domain, never a ui; another domain is reached only through its model or port. `workspace` is the composition root and may also import other domains' ui and controller (user's choice 2026-11-07, 2026-11-10); adapters it gets only through ports in `Options`, which `cmd/workshop` fills (file dialog, preview, history, fonts, store, state, clock, settings files, protocols, cURL, gRPC methods). A nil port falls back to a null one so tests and screenshots need no desktop; a nil `Clock` falls back to `time.Now`. `exceptions` in the layer test is empty. Pure parsers (cURL, GraphQL schema, importers, MCP lists, schema skeletons) are model packages. Go cannot split an `App`'s methods across packages, so everything that reads and writes it stays one package, `workspace/ui/app` (package `app`); a feature that needs little of it is its own package behind a `Host` interface (`calltrace`, `mcpform`, `sentlog`, `settingsui`, `colorpage`, `shortcutpage`), with a fake-host test. Things with no widget in them go to a `controller` package first.
12. **Task 031 closed unrun** (user, 2026-11-07). Nothing was run on Windows or macOS: window and HiDPI, clipboard, file dialogs, browser opener, Cmd shortcuts, font folders and IME are untested there; the Windows `.exe` has no icon (a `.syso` needs a tool that is not approved); `release.yml` has never run on a real tag. Reopen as a task when a machine, a CI runner with a display, or the tool approval exists.
13. **State changes follow Model, Msg, Update, Cmd** (tasks 035 to 041, user approved 2026-11-10). A domain's controller owns a `Model` (plain data, no widget), typed `Msg` values (documented with who sends them) and a pure `Update`: no I/O, goroutine or clock. `Update` returns `(model, []Cmd)` only where the domain has effects (send, dial, save); a `Cmd` runs off the UI goroutine and reports back as a `Msg`. A handler on the UI goroutine applies its message at once (`updateTabs`), because the next line needs the new state; the `bus` carries only what goroutines report, drained once per frame, which marks the frame dirty. The widget state of a model's parts lives in a map in the App keyed by the model object (`App.widgets`). `Update` may type-switch on its message type; the only place the "table over switch" rule yields. Controllers: `workspace/controller/{tabs,autosave,serial,overlay,bus}`, `collection/controller/tree`, `request/controller/editor`, `response/controller/viewer`, `environment/controller/envs` (its `Menu` holds the chip's rows; the App keeps the prompts). `settings/controller/prefs` is the exception: it has no `Model` or `Update`, only the `Msg` types a settings page sends through `Host.Send`, which `App.Send` applies at once on the UI goroutine; some carry functions (`Change.Edit`, `Edit.Edit`, `PickFile.Done`, `Later.Func`, and `MenuItem.Run` in `OpenMenu`), because the page decides what changes and the App owns the settings it changes. Accepted gaps: idle frames build no JSON key or tab comparison (`changeKeys` only on frames with input, a message or a window change; a revision counter was rejected, one missed bump loses an edit); collection, UI state and history writes are one per file at a time, the newest waiting write replacing older (`serial.Queue`); socket sends and pings run from a per-tab ordered outbox; settings `Persist` and image decode stay on the UI goroutine; the window tree is built twice per frame (about 0.18 ms). Rejected: signals, React-style diffing, more controllers behind closures.
14. **A row that overflows takes the overflow from its `Shrink` children** (task 015, 2026-11-14, user's choice over a lower chip cap). `Shrink()` is explicit rather than a reading of `Ellipsis`, because the child that gives room is often a container. After `Optional` children are dropped, the overflow is taken from `Shrink` children first to last, each down to its `MinW`; a row that fits lays out as before.
15. **Dialogs are in-app floating windows with a title bar of their own** (tasks 056 to 058, 2026-11-14, user's choices). Ebitengine has one OS window per process, so no child windows or second process. `Moved(*MoveState)` shifts a `FloatCenter` element by the dragged offset and `DragHandle()` marks what drags it; a control inside keeps its click, a double click centers. Layout keeps the dialog inside the Stack and writes the kept offset back to the state (the one place layout writes). Resize is symmetric about the center; the grab zone is 6 px inside to 4 px outside the border and `DismissMargin(4)` stops the outer strip from dismissing. `DialogTitle` is only title, free room and close, a drag handle all along, on `Hero` with the `hero` gradient and `HeroText`/`HeroMuted` like the window header, with `RoundT("menu")` filling its top corners by alpha (the same corner mask serves `RoundB`, `RoundBL`; the radius comes from `Ctx.Radius`). Controls go in `DialogToolbar`; `DialogSubtitle` is a muted note. `CursorMove` shows only while pressed. Message dialogs have the bar and a close button that runs the panel's `OnDismiss`. The look is in `style.md`.
16. **A System page in the settings shows the system and GPU rendering** (task 059, 2026-11-14, user's request). `settings/model/sysinfo` is the report, read through a port by `systeminfo`, which takes the Ebitengine side as an injected function so tests need no display; `cmd/workshop` wires it, otherwise the page is empty. Values are read at each build of the page, so FPS is what the last redraw saw. Copy puts the report on the clipboard.
17. **Several collections are open at once, each known by its folder** (task 071, 2026-11-15, user's decisions). `collections.Set` holds the open ones in tree order, with no limit; an entry's identity is its folder (`Dir`, "" until the first save), so opening a folder already open focuses it, two entries never share a folder and a new one is appended. Each collection has its own active environment (`Entry.Env`), remembered by name with its folder in `settings.collections`; a request expands with its own collection's variables only, so nothing leaks across, and the header chip shows the collection of the active tab, else of the tree selection, else the first. History files and the sent log key a request by its collection's folder and path; the bare path stays the key of the first or an unsaved collection, so history written with one collection still reads. The first save of an unsaved collection makes its own folder under `collections/`, as New does. Closing the last collection leaves an empty tree with Open and New and makes nothing on disk; closing an unsaved, edited one asks first. The settings list replaces the `workspace`/`environment` keys, which are read only when the list is absent; state tabs and open folders name their collection's folder, and an empty one is the unsaved or first collection, so older files open as a set of one. Reordering is by the root row's menu, not by drag, because a drag moves a node within its collection; root names are bold. Moving or copying requests across collections is out of scope (a later task); such a drop is refused.
18. **Without a dialog program, Linux gets an in-app file browser** (task 068, 2026-11-15, user's decision). The fallback of decision 8 is a file browser dialog built from toolkit widgets, for Open and Save alike, instead of a prompt for the path; a D-Bus portal was turned down because it needs a client library or a hand-written protocol and a running portal service, while the in-app browser needs nothing installed. It is chosen like the native programs, as the last row of a table of choosers, and keeps the `FileDialog` port's contract (one path, save asks before replacing a file). Detection was widened so the browser is rarely needed (2026-11-15, user's decision): zenity, kdialog, yad, qarma and matedialog, ordered by the desktop (decision 8). The browser tells the user which program gives native dialogs in a muted line of its footer (the default taken, 2026-11-15; the user did not choose a place), naming the desktop's program (kdialog on Plasma; zenity on GNOME, Cinnamon, Budgie, Pantheon, Unity, XFCE, LXDE, MATE and LXQt; "zenity or kdialog" on a desktop with no row).
19. **gRPC reads `.proto` files with protocompile** (task 070, 2026-11-15, user's decisions). `github.com/bufbuild/protocompile` parses and links `.proto` sources into the same `protoreflect` descriptors that server reflection gives, so calls use one code path; it was chosen over a hand-written parser on top of protobuf's `protoreflect` (a parser and linker to write and keep up with the language) and over running an external `protoc` (a program the user must install, and its output to read back). Errors carry file, line and column (`model.ProtoError`), the standard `google/protobuf/*` files come with it, and import paths are searched in order, as protoc does. The proto files and import paths are stored per request, not per collection; paths inside the collection's folder are saved relative to it, so the folder can move, and paths outside it absolute; relative paths are written with `/` on every system. The choice is a Proto tab of the gRPC request (user, 2026-11-15): chips Reflection and Proto files, as Auth picks its type; the source stays derived from the files, so choosing Proto files changes only the tab until a file is added, and choosing Reflection removes the files and import paths; the file format is unchanged. Import paths are typed into an empty row (Add path), since the file dialogs pick files only and a folder mode would touch every dialog program (decisions 8 and 18). The debug sample's proto path is found from its source tree (`runtime.Caller`), the sample having no folder of its own.
20. **The dev build has its own user directory** (task 072, 2026-11-15, user's decisions). The default (dev) build keeps settings, state, history, themes and saved collections in `gascoigne-workshop-dev` in the user config directory, the release build in `gascoigne-workshop` as before; the name is `userdir.Name`, split by build tag, and every adapter that writes there takes it from it. The dev build therefore reopens what it remembered, like an install, instead of ignoring the remembered collections (the former `ignoreRememberedWorkspace`); the Example Server is its first-start sample, and screenshot runs and the golden scenes still keep settings in memory. Client configs stay one collection with each configured collection a folder inside it, in the release build only. An unsuffixed directory written by an earlier dev build is left alone: no migration and no warning.
21. **Requests that run commands or read files ask first** (input audit, 2026-11-16, user's decisions). A request that would start an MCP `stdio:` command or read a file outside its collection folder (a multipart `@path`, a file body) asks once through a confirm dialog that names the command or path; Allow is remembered per command line and per absolute path in `state.json` (`trusted`, keys from `model.Access.Key`), and a changed command asks again. Why a prompt and not a refusal: the file browser stores absolute paths, so refusing paths outside the folder would break normal attaching. `.proto` imports cannot leave their import paths (no prompt), and a `.workshop.*` config in the working directory is read as before (decided against). Values captured by a `set` assertion are `Literal` and never expanded again (user's decision); Postman export leaves out literal credentials and secret variable values and keeps `{{variable}}` references; secret collection and folder variables are kept out of `folder.json`. Oversized input is limited rather than refused where it can be: a paste is at most 1 MiB, a response body is shown cut at 2 MiB, settings are clamped (all with the user's answers; the limits are in `architecture.md` Limits).
22. **Every saved file carries its own version** (task 079, 2026-11-18, user's decisions). `state.json`, `settings.json`, `folder.json`, `*.req.json`, `*.env.json`, `.secrets.json`, the history files and every line of `sent.jsonl` start with `"version"`; a missing version is 0, the layout before versions, and a reader per version is picked from a table (`fileversion.Read`; structure and the signal to revisit in `architecture.md` Persistence). The version is per file, not one per collection, and lives in each adapter's wire type, not in the model. A file written by a newer build (user, 2026-11-18): a collection is not opened and the toast names the file and both versions; `settings.json` and `state.json` are read-only for the session (defaults or the empty state, an error toast once, no write of that file, no backup as if broken), recorded as `fileversion.Access` per file; a newer history file shows an error and is overwritten by the next response; newer lines of `sent.jsonl` are skipped and kept until trimmed. Accepted (user, 2026-11-18): the first save after upgrading rewrites every file of a collection once, adding the version line (and wrapping `.secrets.json`), so a collection under version control shows a one-time diff; CHANGELOG.md says so. Moving the decision-17 fallbacks (`workspace`/`environment`, the flat settings form, `Tab.Pane`) into a version-0-only reader is a later task.
23. **The name Postman is allowed where it names the import and export format** (user's decision, 2026-11-18). The common rule against naming other tools in code, docs, tasks and commits yields here: the Postman collection format is a file format the workshop reads and writes (`internal/collection/model/postman`, `postman.Parse`, `postman.Export`, the menu entries and the fuzz target), and a generic name would hide which format a user can import. Everywhere else, other tools stay unnamed.
