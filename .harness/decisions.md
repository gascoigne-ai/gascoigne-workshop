# Decisions

1. **Ebitengine with custom widgets** (user choice). Pure-Go GPU 2D with Wayland/X11 support and one static-ish binary. Cost: every widget, text input and scroll area is ours. First milestone keeps input single-line and the code viewer read-only.
2. **Protocol registry.** REST is real in milestone 1; WebSocket and MCP are registered stubs that return "not implemented", so the UI path is exercised end to end.
3. **Sibling bare repo** like the other gascoigne projects; shared harness via `.harness/common`.
4. **Toolkit split: `widget` + `vml` + app.** The reusable GPU toolkit and the view DSL are public packages with no knowledge of requests or protocols, so they can move to their own repo later. The app only holds state, handlers and views.
5. **VML is a Go-native DSL, not a template language.** Typed builder functions with chained attributes and Vue-like `If`/`For`/`Field`. The Go compiler checks it, refactors keep working, and no parser, reflection or generator is needed. A text template syntax can be added later as another front end that emits the same nodes.
6. **Views are rebuilt every frame.** State stays in the app; there is no virtual DOM diffing or reactive graph. Widgets that need identity across frames (text field, code view) take a pointer to app-owned state.
7. **Streaming protocols and a hand-written WebSocket client.** `proto.Protocol` keeps its one-shot `Send`; protocols that stay connected also implement `proto.Streamer.Connect`, which returns a `Session` (an ordered `Events()` channel, `Send`, `Ping`, `Close`). A slow consumer blocks the reader instead of losing messages. The standard library has no WebSocket, and the rules allow no new dependency, so `internal/proto/ws` implements RFC 6455 (handshake, framing, masking, fragments, ping/pong, close codes) in about 400 lines; its server-side handshake exists for tests.
8. **Themes are data, per-control.** Colors, corner radii, gradients and outlines live in embedded JSON theme files (variables, colors, controls), not in Go, so the look can change, be flattened or squared (settings `corners`, `flat`) without touching widgets. Elements name a control style (`vml.Control`) instead of picking a gradient or border themselves. The format is our own small JSON rather than a CSS or editor-theme dialect: it has to carry radii and gradients, and parsing stays in the standard library.
9. **Collections are a tree of JSON files** (`internal/store`). One directory per folder (`folder.json` with the name, root variables and the child order), one `*.req.json` per request, indented with a stable key order so diffs are small and git-friendly. File names are slugs of the names, made unique with `-2`, `-3`; the real names live inside the files, so any characters survive. Credentials (token, password, API key value) are written to `.secrets.json`, keyed by request path and listed in `.gitignore`, never into request files. Saving only removes `*.req.json` files and folders with a `folder.json`; other files in the workspace are left alone. Loading puts files the order list does not know after the listed ones, by name, so hand-made files appear.
10. **MCP is a hand-written JSON-RPC client** (`internal/proto/mcp.go`), no SDK, for the same reasons as decision 7: the needed part of the protocol is small (initialize, lists, calls, ping over streamable HTTP and stdio), the dependency would be large, and the raw message log the UI shows is simply what the client already handles. It implements `Streamer`; `Send` is the one-shot form (connect, `tools/list`). A server URL starting `stdio:` runs the rest of the line as a command.
11. **Declarative views are HTML-style templates on the same runtime** (`uitoolkit/tmpl`). A `.vml` file is XML with HTML's leniency (bare flag attributes, entities), parsed with `encoding/xml`: no new dependency, no second runtime. It builds the same `*vml.El` tree as the Go DSL, so the two styles mix and a view can move from Go to a template one at a time. Elements and attributes are tables (`elements`, `attributes`), bindings are `{{path}}` lookups in a `Scope`, there are two directives (`if`, `for="x in xs"`) and `onclick` names a `func()` of the scope. No expressions and no code in templates: logic stays in Go, which keeps templates checkable. Errors name file and line. Tag `col` is not an HTML void element here because no HTML auto-close table is used.
